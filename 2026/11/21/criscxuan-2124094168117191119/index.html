自从吸上了 T3 Code ，爽感堪比 GTA-6

发表于2026-11-21|行业观察
|浏览量:

本文转载自 X 博主 @criscxuan（cxuan） 的长文，原文链接，版权归原作者所有。

用 Coding Agent 这么久了，估计很多小伙伴都遇到过这种问题，平常开发或者办公会用到很多 Coding Agent ，不同 Agent 中的模型不一样，虽然你可以通过开源网关把许多模型接入到一个 Agent 中，但你也会遇到不同 Agent Harness + 模型适配度问题。

给大家看一下我日常用的 Agent 。。。

我就经常想切 ZCode 结果切成 OpenCode 去了。。。难顶

而且一言以蔽之：自家模型还是用自家的 Harness 最好，至少。。。可能不会遇到稀奇古怪的问题。

既然自家模型配自家官方 Harness 最稳，那桌面上就不可避免会装十来个客户端和 CLI，来回切换窗口、分别导入项目、找回历史会话都很割裂。

于是就会衍生出来一个问题，那就是有没有办法保留各家原厂 Harness 的执行能力，只在最外层用一个统一入口把它们收编管理起来？

这就是今天我想说的 T3 Code。

T3 是什么

T3 Code 是由 Ping Labs（Theo Browne 团队）发起的开源项目，基于 MIT 协议开源。官方对它的描述是这样的 ：Agent Harness Control Surface（多 Coding Agent 统一控制面板）。

T3 Code 是由 Ping Labs（Theo Browne 团队）发起的开源项目，基于 MIT 协议开源。官方对它的定位很克制也很精准：Agent Harness Control Surface（多 Coding Agent 统一控制面板）。

它和常见大模型中转客户端最大的区别在于：

  1. BYOS ，不转卖 Token
    T3 Code 本身不卖模型额度，也不替换底层推理逻辑，而是直接接管你本机已经安装、登录好的官方 CLI 和 Agent。你原来在各家订阅的账号和配置，接进来就能直接用，底层依然跑原厂 Harness，最大程度避免魔改适配带来的玄学 Bug。
  2. 原生兼容 ACP 协议与 ACP Registry
    除了内置适配的一线 Agent，T3 Code 还全面支持 ACP（Agent Client Protocol） 以及官方 ACP Registry 生态。只要支持 ACP 标准协议的工具（例如 Qoder CLI、Kimi Code、DeepSeek Harness、goose、Junie 等）或者自定义的本地 ACP 命令，都能一键接进同一个面板里调度。
  3. 跨端同步 + 远程手机控制
    T3 Code 提供 macOS / Windows / Linux 桌面客户端、Web 端以及原生的 iOS / Android 手机端。后端以本机服务运行，通过局域网、Tailscale 或内置的 T3 Connect 安全隧道就能远程连上家里或公司电脑上正在干活的 Agent，随时随地看进度、批权限、发指令。
  4. Git Worktree 隔离与任务编排能力
    支持为每个任务线程自动开独立的 Git Worktree 和分支，多个 Agent 同时改同一个项目也不会互相覆盖文件；右侧直接集成 Diff 对比、提交、Push 和 PR 工作流，并且支持在单条主线程里把子任务跨 Agent 委派（Delegate）给不同的模型协作完成。

如果你想快速体验，可以直接通过命令行或包管理器安装：

macOS 安装桌面端

brew install –cask t3-code

或者直接用 npx 临时跑起来体验

npx t3@latest

或者一句话直接让 AI 给你装一下即可。

Gemini 最近发了不少新模型，一直以来用反代接 Gemini 都容易封号，所以很多时候不得已只能用那个不太顺手的 Antigravity 反重力客户端。而在 T3 Code 里能稳定用上 Gemini，是 Google 把自家的 Antigravity 做成了标准 ACP Server 并上架到了公开的 ACP Registry。

这波确实强。

比如我让 T3 用 Qoder 审查了一下当前代码。

刚看到它能把 Qoder 叫出来干活时，我差点以为它是靠 Computer Use 直接去点开 Qoder 桌面端跑任务的，查了一下底层实现并结合上面的日志发现，其实不是这么回事：T3 Code 并不是走 GUI 桌面自动化去操作 Qoder 客户端，而是主 Agent 通过 T3 内置的编排层（内部 /mcp 委派接口）拉起一个独立子线程，再通过 ACP 协议 在后台直接调用本机安装好的 Qoder CLI 执行任务。

子线程跑完后再把结果交回主线程。相比 Computer Use，这种基于标准协议拉起 CLI 子进程的方式要轻量、稳定得多。

T3 的右侧 Toggle right panel 我觉得做的不错，可以直接查阅代码，也可以查看 changes ，虽然这些都是必备基操，但是 T3 的易用性挺好。

架构

看完这些实测表现，再回过头来看一下 T3 Code 的架构设计，就能明白它为什么既能兼容这么多 Agent，又能把手机远程、Worktree 隔离和跨 Agent 编排搞的这么丝滑。

（手机远程我没测试，不过我觉得这个功能大家应该都了解了吧 。。）

整体来看，T3 Code 在结构上做的很干净：

  1. 前端控制面（apps/web + apps/desktop + 移动端）
    Web 端基于 React + Vite 构建，负责呈现线程列表、Diff 审阅和审批交互；Electron 桌面端其实只是把同一套前端界面套上原生窗口壳并托管本地后台服务，而 iOS / Android 手机端、局域网浏览器、Tailscale 以及 T3 Connect 隧道连进来的也是同一个服务后端。
  2. 本地核心引擎（apps/server）
    真正的控制中枢是跑在 Bun 上的 apps/server，它与前端之间通过 WebSocket + 轻量 JSON-RPC 协议通信，并由 packages/contracts约束接口契约。服务端内部由 OrchestratorV2 负责编排多轮执行与事件流，由 ThreadManagementService 统一托管持久线程、队列、重连恢复、中断控制以及本机的项目/Worktree 环境边界。
  3. App-owned 内部 /mcp 服务与跨 Agent 委派
    T3 Code 自己向上层运行的 Agent 暴露了一套内部 /mcp 端点，把子任务委派、线程读写、定时任务和预览控制包装成标准工具。于是哪怕主线程跑的是 Codex，也可以直接通过内部 MCP 去拉起另一个 Kimi、Qwen、DeepSeek 或 Qoder CLI 子线程协同干活。
  4. 原厂 Harness 与 ACP 双轨执行 + Worktree 隔离
    最底层完全不重写也不魔改模型推理逻辑：一边直接对接你本机已经登录好的官方 CLI（Claude Code、Codex、Antigravity 等），另一边通过标准 ACP 协议 接入 ACP Registry 生态里的第三方工具；配合服务端动态分配的 Git Worktree，把并发改代码隔离成互不干扰的分支环境。

写在最后

实测一圈下来，我觉得 T3 Code 我用着非常顺手，它没有硬塞一个大模型聚合套壳客户端，而是做到了控制层面，相当于 T3 Code 就是一个汇报中枢，它不做 Harness 适配也不做模型调优，它就简简单单的把多个 Agent 协调干活和统一入口做到了易用和简洁。

我觉得这就够了。

也许简洁和好用才是王道。

如果你平时和我一样，桌面上经常同时开着好几个 Coding Agent 切来切去切觉得麻烦的话，那么 T3 Code 绝对是目前最值得一试的开源方案。
