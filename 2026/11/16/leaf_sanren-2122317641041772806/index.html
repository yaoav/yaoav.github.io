超简单 DeepSeek Harness 实战：不认证/不申接口，48 秒把 X 长文推到公众号草稿箱（附开源 Skill）

发表于2026-11-16|行业观察
|浏览量:

本文转载自 X 博主 @leaf_sanren（Leaf Yeah!） 的长文，原文链接，版权归原作者所有。

各位，今天来看一个刚用 DeepSeek Harness（下面简称 DSH）跑通并开源的 Skill：wechat-draft-push。

一句话：不用企业认证、不用申请 AppID，把仓库丢给 DSH（或任何编程 Agent），一条命令 48.3 秒，把写好的 X 长文直接送进你自己的公众号草稿箱。

起因很现实：我 11 月 9 号在 X 上发了一篇《DeepSeek harness 万字长文》，跑了 20 万阅读。三天后在微信里一搜，排第一的是别人的公众号，标题一字没改。申诉打不开推特链接，截图也不认——平台维权只认公众号里的发布时间。

想不被搬运，就得「先发公众号，再发 X」。我们用 DSH 把这套原本二十分钟的体力活压成一条命令，MIT 协议开源。当然坦诚说，这套工具靠的是本机 Chrome 和 Python 脚本，不用 DSH，用 Claude Code、Codex、WorkBuddy 一样能跑。

开源地址：https://github.com/YeJe-cpu/wechat-draft-push

一、为什么不走官方接口：11 篇长文里只有 3 篇能过

大部分公众号自动化教程的第一步，都是教你申请开发者资质、拿 AppID 和 AppSecret、配 IP 白名单，然后调官方的 draft/add 接口。

真拿长文去跑，前面卡着三堵墙：

  1. 资质门槛：只想写文章防搬运，一上来就要配开发凭证和白名单，很多人第一步就被劝退了。
  2. 个人号权限：2025 年 7 月官方回收了一批发布类接口权限，个人未认证号到底能不能建草稿，社区到现在还在吵，有人报 48001 错误，有人能通。
  3. 两万字符硬墙：接口限制正文 2 万字符、标题 32 字。关键在于它数的不是你的汉字，是排完版之后的 HTML 字符串长度。

我拿被搬运的那篇《DeepSeek harness 万字长文》实测过：读者看到的是 8,045 字，排成带内联样式的公众号 HTML 后，直接变成 35,595 个字符，光 style=”…” 就占了六成——放大了 4.4 倍。

拿我们第一批 11 篇长文挨个过一遍：HTML 长度普遍放大 3.5 到 4.9 倍，结果 5 篇正文超限、3 篇标题超 32 字，能直接过官方接口的只有 3 篇。

二、这个开源 Skill 能干什么，不能干什么（5 条硬边界）

既然官方接口卡死长文，那就换个思路：不走接口，直接用 Chrome 远程调试协议（CDP）连上你日常已登录的浏览器，像人一样在后台编辑器里操作——后台编辑器允许 64 字标题、120 字摘要，正文没有 2 万字符上限。

能干什么：

  • 一键推草稿：自动转码排版 → 传图换微信图床 → 填标题摘要正文 → 设封面 → 存草稿。实测 6 张图、3,700 字的文章耗时 48.3 秒。
  • X 长文直接扒：内置 x2wx.py，可以从 X 长文链接直接抓回正文、配图、封面和嵌入内容。
  • 空跑校验与断点续传：–dry-run 只校验本地材料不碰后台；中途断了重跑，已传图片和草稿记录都存着本地台账，不会重复传图、不会建两份草稿。

不能干什么（5 条硬边界）：

  • 只存草稿，绝不发表：不点发表、不群发、不发预览、不碰作者和原创声明。最后那一下永远由人打开手机确认再点。
  • 只支持串行，不支持并发：一次推一篇。同一个浏览器会话并发写编辑器会互相踩踏，直接把草稿写乱。
  • 不做多账号矩阵：只服务单账号日常同步。

四、底层揭秘：借你自己的 Chrome，到底怎么把文章写进去的

很多人好奇：不走接口、不装浏览器插件，Python 脚本是怎么通过一个 Chrome 调试口子把图文排进公众号的？

整件事分两部分：进后台前的预处理，和 进后台后的浏览器实操。

进后台前，先过两道本地处理：

  1. 改词过审：X 上能写的网络环境、外链、「评论区」「求转发」，进公众号前得先洗成「留言区」「点个在看」；截图里的字也算，带敏感词的配图必须换掉。
  2. Markdown 转内联 HTML：公众号正文不认外部 CSS，md2wx.py 会把所有标题、列表、引用、代码块全展开成内联样式。

**进后台后，CDP 代理（**cdp-proxy.mjs）借你已登录的 Chrome，干了四件「像人一样」的硬核动作：

  • ① 原地上传图片换图床
    脚本在本机 127.0.0.1:8766 起一个临时图片服务，然后通过 CDP 在公众号页面上下文里直接 fetch 本地图片，POST 给微信后台自己的素材上传接口，拿到 mmbiz.qpic.cn 图床链接并替换进 HTML。因为请求发自你已登录的页面，自带全部登录 Cookie，不用额外鉴权。
  • ② 找对编辑器、等够渲染时间
    公众号后台有两个 .ProseMirror 编辑器（一个正文、一个标题）。而且标题框 .title-editor 只是父元素 class 前缀，实际元素是 title-editor__input。用 execCommand(‘insertText’) 填完标题后，隐藏字段 #title 同步有约 1 秒延迟，必须等 1.2 秒再校验。
  • ③ 派发一次真实粘贴事件
    正文不是直接改 DOM，而是通过 CDP 往正文编辑器派发一次真实的 paste 事件——而且粘贴后的渲染是异步的，刚贴完去数图片会数出 0 张，必须等够 6 秒再检查。
  • ④ 绕过前端限制设封面
    公众号的封面上传框在初始页面里根本不存在，它是点击「从图片库选择」之后动态生成的。脚本必须先点开弹窗、等 2 秒让 webuploader 绑定好事件，再用 CDP 底层的 DOM.setFileInputFiles 注入封面文件（用 JS 伪造上传事件微信根本不认）。

五、实战踩坑：3 个 Agent 踩出来的 18 个坑，最要命的是这 4 个

这套工具不是拍脑袋写出来的。仓库 references/pitfalls.md 里记了整整 18 个坑，全是我们用 DeepSeek Harness、Claude Code、WorkBuddy 三个 Agent 实打实跑第一批 12 篇稿件时翻车踩出来的：

  • 坑 1：粘贴正文重试一次，草稿里直接叠成两份
    后台编辑器的粘贴是「追加」不是「替换」。早期脚本遇到卡顿重试了一次，结果草稿箱里开头重复了整整一遍。现在铁律是全流程只允许派发一次 paste，失败了就关掉标签页重开，绝不原地重试。
  • 坑 2：数图片永远数出两倍（8 张变 16 张）
    贴完正文去核对图片数量，脚本每次都报数错。扒开 DOM 才发现，编辑器每插一张图，后面都会自动跟一个 占位符。不把 mmbiz.qpic.cn 过滤出来单独数，校验永远对不上。
  • 坑 3：封面传成了正文截图，脚本还报 ✅
    这是最隐蔽的「假成功」。打开图片库时默认会选中列表里第一张图，早期脚本只校验「封面区有没有 mmbiz 链接」——结果旧图或正文截图都有这个前缀，直接假通过。现在改成了：**上传后必须核对图片库选中项的文件名等于 **cover.jpg，换封面时必须要求新 URL 不等于旧 URL。
  • 坑 4：页面卡在「自检中」25 秒，保存其实已经入库
    微信前端偶尔会在点「保存为草稿」后卡死：按钮变灰、文字被清空、URL 一直不出 appmsgid。如果你直接判定失败并重跑，草稿箱里就会多出一份一模一样的草稿。所以铁律只有一条：报错先去草稿箱看一眼，在里面就只补台账，绝对不要重跑。

六、速查表（收藏备用）

  • 仓库地址：https://github.com/YeJe-cpu/wechat-draft-push（MIT）
  • 兼容 Agent：DeepSeek Harness（DSH）/ Claude Code / Codex / WorkBuddy
  • 必开设置：Chrome 打开 chrome://inspect/#remote-debugging 勾选允许
  • 启动代理：node scripts/cdp-proxy.mjs（Node.js 22+，无第三方依赖）
  • 环境自检：python3 scripts/check.py <文章目录>
  • 空跑 / 推送：python3 scripts/push.py <文章目录> [–dry-run]
  • X 长文扒取：python3 scripts/x2wx.py <X长文链接> <输出目录>
  • 排错与验收：看仓库 references/pitfalls.md（18 坑）与 verify.md
  • 发稿顺序铁律：新文章先发公众号，再发 X

最后

说到底，解决被搬运的办法从来不是去跟平台打官司，而是把「先发公众号、再发 X」的同步成本压到够低。现在有 DSH 和这套开源 Skill，48 秒就能进草稿箱，以后写完顺手先推一遍再发推，也就省心了。
