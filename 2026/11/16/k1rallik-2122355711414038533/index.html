Graphs, Loops & Reverse Engineering: Build Your Own AI Team (Full Guide)

发表于2026-11-16|行业观察
|浏览量:

本文转载自 X 博主 @k1rallik（BuBBliK） 的长文，原文链接，版权归原作者所有。

You ask Grok Bot to research an idea. Send the findings to Claude. Move the result into ChatGPT for a second opinion.

An hour later, you have three chats, several conflicting answers, and a job carrying context between them.

You still remember the requirements, catch the mistakes, and decide what happens next. Every handoff depends on you.

To delegate more of that work, you need a process:

  • Reverse engineering turns an existing product into observable requirements.
  • A graph defines the tasks and their dependencies.
  • A loop checks a result and sends it back for correction.

Let’s put them together around one example: building your own version of a tool that turns articles into social media cards.

1. Reverse engineer the behavior

A screenshot can show you the layout. It cannot tell you what happens when a title is too long, an input is empty, or an export contains ten cards.

Before asking a model to build anything, investigate the user journey.

Provide screenshots, descriptions, and observations from trying the product. If the model has browser tools, it can help inspect the public interface.

Start with this prompt:

Analyze the product’s observable behavior. Describe the user’s inputs, actions, outputs, and error states. Separate observations from assumptions and unknowns.Propose a minimal version we could build, with an acceptance check for each feature.

The output should contain requirements you can test:

“The user can edit generated cards, change their order, and export images in that order.”

A working interface does not reveal the original source code, prompts, or architecture. You are reconstructing enough behavior to design your own implementation.

2. Give each model a bounded job

For this example, try this starting allocation:

  • | Participant | Job | Deliverable |
  • |—|—|—|
  • | Grok Bot with search access | Investigate public discussions and complaints | Findings with sources |
  • | Claude | Analyze workflows and write the specification | Requirements and acceptance criteria |
  • | ChatGPT with development tools | Implement the agreed scope | Code and check results |

These are proposed roles, not a universal ranking. Change them based on results and available tools.

A chat that can suggest code cannot necessarily run it. A model without search access cannot independently gather current discussions.

Give each participant a defined output. For research:

Find concrete complaints about tools that turn text into social cards. Include source links. Distinguish recurring problems from isolated opinions, and identify where evidence is insufficient.

Research informs the scope. It does not automatically expand it: one complaint is not enough reason to add another feature.

3. Draw the graph before running the tasks

A graph makes dependencies explicit.

Audience research and interface analysis can happen independently. Implementation needs an agreed specification.

Reference materials feed interface analysis and audience research in parallel. Their outputs inform the specification and checks. Implementation then goes through validation: failed work returns for repair; accepted work moves forward.

For each connection, identify what passes across it: a requirements document, source findings, code, or a failure report.

Also check for shared resources. Two tasks may have independent inputs but still conflict if both edit the same file.

For a small job, one worker and a check may be enough. Another model needs a useful responsibility to justify the coordination cost.

4. Define what “done” means

Every task needs a compact contract.

For card export:

Write these conditions before implementation. Otherwise, it is easy to accept whatever the model happened to build.

Passing checks only establishes what those checks cover. A successful export test says nothing about whether the generated cards preserve the article’s meaning.

5. Build a loop that can reject work

A loop connects execution to actionable feedback:

Produce -> Check -> Correct -> Check again.

Suppose a long title overflows its card.

“Make it look better” leaves the worker guessing. A useful failure report provides a reproducible case:

Use code for exact checks such as file counts, dimensions, and required fields.

For meaning or visual quality, use human review or a separate model with explicit criteria. Ask it to identify defects and provide evidence.

Agreement between models is not proof. Sources still need verification, and executable work needs to be run.

6. Return the failed unit

If export breaks but the editor works, send export back for repair.

Regenerating the entire application creates unnecessary changes and increases the amount of work you must verify.

Each return should include the affected unit, failure evidence, expected behavior, and permitted scope. After the local fix, run the relevant integration checks too.

Set a retry or spending limit. Three correction attempts can be a starting setting, but repeated failure does not automatically mean the plan is wrong. The environment, requirements, or checker may be at fault.

When the limit is reached, preserve the attempts and escalate for diagnosis.

7. Save lessons with evidence

After fixing the title overflow, save a reusable lesson:

Feed it into future requirements and checks.

An entire chat history also contains abandoned ideas and incorrect assumptions. Extract confirmed lessons, record their scope, and allow them to be revised.

8. Automate the handoffs

You can test this process manually with shared files before building an orchestrator.

Keep the reference materials, specification, check results, and accepted decisions together. Pass each participant the artifacts it needs.

Once the handoffs are repeatable, a coordinating program can call model APIs, transfer results, run checks, and enforce limits:

Subscriptions to separate chat products do not create this integration automatically.

Define where human judgment belongs: scope, unresolved requirements, and approval for consequential actions. Reversible local changes can have different permissions from publishing or modifying production data.

Start with one complete workflow: paste text, edit cards, export images.

Compare the process against a single-model attempt. Track time, cost, remaining defects, and how often you intervene. If coordination adds more work than it removes, simplify the graph.

Every time you have to type “continue,” restate a requirement, or explain an avoidable failure, record why. Use those observations to improve the next run’s transitions, checks, and task boundaries.
