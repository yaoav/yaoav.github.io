Mode Engineering: Stop Paying a Top Model for Every Step

发表于2026-11-20|行业观察
|浏览量:

本文转载自 X 博主 @rincyXIII（rincy） 的长文，原文链接，版权归原作者所有。

How to give every piece of work the right amount of intelligence: the mode per channel, the script for the fixed steps, and the run that never needed to happen

In 2024 Sam Altman posted four words that every AI builder remembers

Tokens did get cheaper

Running AI every day did not get simple

Because the price of a token was never the real problem

The real problem is what you send to the most expensive model

The daily report

The ticket tagging

The hourly check that finds nothing 23 hours a day

The sum of a column

The date format

The “is there anything new” question asked again and again

None of those need a top model

Most automations send them to one anyway

Boris Cherny, who created Claude Code, wrote the new rule in one line

Number two is the one nobody engineers

How much effort

Not per prompt

Per place, per job, per step

That is mode engineering

This article is about building that split with an AI employee who already has every lever in it: Viktor

The expensive mistake inside every automation

An automation looks simple from the outside

Zoom in and it is a chain of small steps

Take the most common one there is: the morning revenue report

Five steps with one right answer

Two that need a model

When the whole thing runs as one AI run, the model does all seven

That creates four problems

The model does the arithmetic

It reads 40 rows into context and sums them in its head

A script does that for free and never gets it wrong

The run happens on empty days

Nothing closed on Sunday

The model still opened the CRM, pulled zero rows, reasoned about it, and wrote “no new deals”

You paid for a full run to learn nothing

The mode was set once, a long time ago

Someone built the report on the strongest model because it worked

It still runs on it, every day, for three lines

Nobody owns the choice

“Which model should I use for this?” gets answered per person, per day, from memory

The answer drifts

And the person typing is the worst person to answer it, because they are busy doing the actual work

The deeper problem is architectural

Judgment and plumbing have been collapsed into the same run

Mode engineering begins by separating them

Four kinds of work

Every step in every job falls into one of four boxes

Judgment a human reads

Strategy questions

A reply to an upset customer

A launch post

A brief from a messy thread

Quality is visible here and mistakes are public

Give it the strong mode

Routine a human reads

The daily digest

The standup summary

The ticket triage note

A human reads it, but the shape is the same every day

Give it a cheaper mode and check that it still holds

Work nobody reads as prose

Tagging

Sorting

Pulling fields into a sheet

Yes / no checks that feed the next step

You are paying for sentences nobody sees

Give it the cheapest mode

One right answer

  • Sums
  • Queries
  • Dates
  • Thresholds

“Did anything change since the last run”

This is not a model job at all

Give it a script

Most teams have only one box

Everything goes to the model they like best

Viktor is built for this split

Viktor is an AI employee

He lives in Slack, Microsoft Teams and email. He connects to 9,800+ tools. He has his own computer in the cloud where he writes and runs code

79,000+ teams have hired him

Two things make him the right place to do mode engineering

  • He is multi-model
    The mode is a setting on the employee, not a second subscription. The hard question and the daily digest go to the same hire, on different modes
  • He writes code
    The steps with one right answer can leave the model and become a script he set up himself, in the same workspace, with the same tools

The model choice has been in the product since February. His co-founder announced it with the detail that matters most

Cost you can see before the run is the first half of mode engineering

The second half is deciding it once, so nobody has to look at a badge fifty times a day

One honest line before the setup, because everything below depends on it

Viktor does not choose the mode for each task by himself. You set the defaults. He works on the mode the place or the task is set to, and anyone can override it when the default is wrong

That is the point

The choice gets made once, by the person who knows the work

Lever 1: Set the mode once per place

Viktor’s model settings have four layers, from his settings docs

The layer that does the most work is the channel

Why the channel is the right unit

Work already sorts itself by channel

#research gets hard questions

**#standup **gets summaries

**#intake **gets things to tag and route

Setting the mode per channel matches the effort to the work without anyone thinking about it

Nobody picks a model in #standup

They just ask Viktor in the channel where the work belongs

The dialog shows its own cost

When an admin changes channel default models, the dialog shows the credits each channel spent over the last 30 days and an estimate of the monthly change

You see the effect before you press save

That is the opposite of how most teams change models: switch, wait for the invoice, guess

Old threads keep their model

A thread that already has its own model keeps it when the channel default changes

New threads pick up the new default

So the change is safe mid-week. It takes effect as new work starts

The best routing rule in the docs

The docs do not say which model sits behind each mode

They give something more useful: one sentence about scheduled tasks that is worth copying everywhere

Viktor defaults to smart. You can ask for balanced for lower-cost routine work, or cheap for runs that write nothing people read

“Write nothing people read”

That is the whole routing logic in five words

If a human reads the output, quality is visible and a mistake costs you

If nobody does, you are paying for prose that goes straight into a sheet

Here is how I would map a team

Five settings

After that, picking a model stops being part of anyone’s day

The exceptions are one word

Sometimes a message in a Balanced channel deserves more

!fast runs one reply on the workspace’s fast model

!deep runs one reply on the workspace’s deep model

Admins choose which models those are under Model overrides. Every reply says what it ran on in its footer, so nobody has to guess afterwards

Admins can also add custom commands that pin a model, a reasoning level and a speed, up to 10 per workspace

This is what “I stopped picking models” means in practice

The choice still exists

You only make it when the default is wrong

Lever 2: Stop the runs that have nothing to do

The cheapest run is the one that never starts

And there are a lot of runs that should never start

Look at what teams actually use an AI employee for over time. The team behind Viktor shared their own numbers last month

Teams build first, then keep him around to watch

That is the right instinct

It is also where empty runs live

A monitor asks “did anything change?” on a schedule

Most of the time the answer is no

If every one of those questions is a full AI run, the bill grows with the clock, not with the work

The condition script

Viktor’s scheduled-tasks docs describe exactly this fix

He can add “a condition script that runs before each scheduled run and skips the run when there is nothing to do”

The question “is there anything new?” has one right answer

So it goes to code

The model only wakes up when there is something to think about

The warning worth listening to

The docs add one more detail: Viktor warns when an AI task would run more than about six times a day

If you see that warning, the task is usually a condition script waiting to be written

Ask for it in one message

That last line matters

Every action that matters waits for a yes from you. A task that quietly stopped posting is not a saving

Lever 3: Move the fixed steps into code

This is the lever with the biggest effect

It is also the one most teams never pull

Boris Cherny made the case for it in July, about Claude Code, and it applies to every automation

Read that again with a daily report in mind

The model could sum the deals every morning

That uses tokens and might get it wrong

Or the sum can become code once, and be right forever

Three shapes of a recurring job

Viktor can run a recurring job in three shapes, from his scheduled-tasks docs

He writes the scripts himself, on his own computer in the cloud. You describe the job in chat, he sets it up

He also writes a plain-language explanation of every new or changed script, so a non-engineer can read what it does before saying yes

The morning report, rebuilt

The model still does the part that needs a model

It stopped doing the arithmetic, the fetching and the empty-day check

And because it now gets five numbers instead of 40 rows, the run it does make is shorter

The ask

Jobs with no judgment at all

Some jobs have no judgment step

“Copy yesterday’s signups into the sheet and post the count”

There is nothing to decide

That job should not start an AI run. It becomes a script task

The same split for events

Event triggers start work when something happens: a CRM event, a webhook, a message in a channel

Viktor’s trigger docs describe two handlers. One runs Viktor with your instructions. One runs a Python script, which “suits high-volume events”

A webhook that fires 500 times a day where 490 need no thought belongs to the script handler

And for periodic checks, the docs say a scheduled task “is usually cheaper, and Viktor may suggest one”

Where code is the wrong answer

Scripts remove one failure class. They add another

  • Script cannot notice the unusual
    If the CRM renames a field, the sum is wrong and the script does not know. Keep a check in the AI step: “if the numbers look off by more than 3x, say so instead of writing the report”
  • Scripts have limits
    Script handler on an event trigger stops after 10 minutes and pauses itself after three timed-out runs in a row. A paused job is a report nobody gets
  • Judgment does not become an if-statement
    “Decide what is worth saying” written as code becomes a report that says the same thing every day

Keep the model on the part that needs a model

Move everything else

The checkup: ask him where the credits go

Here is the step everyone skips

They set the modes, it feels cheaper, and they never look

With Viktor, looking is one message in any conversation

From his usage docs, this is what he can answer in chat

Two limits worth knowing

He only reads this data. Plan and credit changes go through the Billing page, by an admin

He does not give a ready-made forecast for when credits run out. He compares your balance with your recent daily spend, which is honest, and enough to see trouble coming

Per-teammate and per-Space breakdowns are for admins. Admins also get a direct message at 70% and 90% of the workspace’s credits, unless auto top-ups are on

Read the answer like a bug report

The answer is almost always lopsided

A few things cost most of the credits

So the question is not “how do we spend less”

It is “what are the top three, and which lever fits each one”

Then let him propose the fix

You approve what makes sense

You keep the receipts for the next section

The Usage page is the receipt

The chat checkup is the quick version

The Usage page is the proof

From Viktor’s usage docs: admins see it for the last 30 days or the current billing period. Summary cards, a daily spend chart, and the costs of conversations and scheduled tasks. Depending on the workspace, there are views per teammate, per scheduled task and per Space

The scheduled-tasks view sorts by total credits, total runs or last activity

That sort is the whole audit

Do it the week before a change and the week after

Same five steps. Same three numbers

That is the only honest way to say “we spend less”

Not “it feels cheaper”

Before and after, from the same page

The 15-task mode test

A mode map on paper is a guess

Run it against real work before the team relies on it

Fifteen tasks the team actually does, each sent in the channel it would normally go to

For each one, write down four things

Then read the results by mode, not by task

If everything passes on the cheap modes

Your map is too generous somewhere. Move one channel down and rerun its tasks

If writing fails on Balanced

Move those channels to Smart. Writing a human reads is where a lower mode shows first

If data needs !deep to get the numbers right

That is usually a sign the numbers should not come from a model at all. Lever 3

If D3 and D4 pass on Cheap

That is the expected result. A classification and a yes / no. That is the shape of most recurring jobs, and the shape that saves the most once it runs every day

Save the 15 prompts in a doc. Rerun them after any change to the map

A map that passed last month is not proof for next month

The bill outside the employee

Half of the AI bill is not in Viktor at all

It is the subscriptions the team collected before

When the work goes through one AI employee, some of that stops being used

Not all of it. Be precise about which

Cancel what nobody used in the last 30 days

Keep what someone uses for work Viktor does not do for your team. There usually is something, and that is fine

When you still pick the model yourself

The honest section

A mode map handles the normal day. It does not handle everything

The hard question in the wrong channel

A strategy question in #standup, which runs on Balanced

Use !deep, or ask it in the channel set to Ultra

The default is for the usual, not the exception

Writing that will be published

A launch post. A reply to an upset customer. A page on the website

I would not leave those to a lower mode to save a few credits

The cost of a bad sentence in public is higher than the cost of a better model

Work you do not understand yet

The first week of a new kind of job, run it on Smart

Move it down once you know what good output looks like and you can see the lower mode still produces it

A task that started failing

If a task on Balanced or Cheap starts producing output people complain about, move it up first and debug second

Your own experiments

Some people keep a personal subscription to try new models the day they ship

That is a personal choice

It does not need to be a team bill

The math

There is no Viktor pricing in this article, on purpose. Prices change, and they live on Viktor’s own page

The math does not need prices

It needs a formula and your own Usage page

Every lever changes exactly one term

Here is an illustration with run counts only, so you can see the shape without anyone’s prices

Same output

A tenth of the AI runs, in that illustration

Then the second lever on what is left. If the pre-run script hands the AI run five numbers instead of 40 rows, each of those 72 runs does less work

You do not need to predict the saving

Make the change. Wait a week. Read two numbers on the Usage page for that task: total runs and total credits

That is the math

Failure modes that look like savings

The mode is too low on work people read

The output gets a little worse and nobody says anything for two weeks

Then someone stops reading the digest

Rerun the 15-task test after every change to the map

A locked channel nobody remembers

A locked channel ignores the change you just made

Check the Locked label before you wonder why a channel did not move

Old threads on old models

A thread that already has its own model keeps it

A long thread in #research will not pick up a new default. Start a new thread when it matters

Scripts that break quietly

A renamed field. An expired connection. A script that hits the time limit

Keep a sanity check in the AI step, and look at the task page when a report goes missing

Running out mid-month

At zero credits, Viktor pauses and saves the blocked request. It replays only if credits come back within 8 hours

The 70% and 90% alerts exist for a reason. Read them

Two owners for one job

A script task and an AI task both post the same report

Now there are two reports

One recurring job, one owner

Saving on the wrong thing

The cheapest report is the one nobody reads

If a lower mode or a script makes the output worse, the saving is not real

Move it back up

The mode engineering playbook

Step 10 is the one that tells you whether any of this worked

Everything before it is a guess with good reasons

The launch checklist

Before you tell the team the new setup is live, check

If several are unchecked, the setup is not cheaper yet

It is just less visible

The real shift

For two years the question was “which model is best”

It was the wrong question for most of the work

The better question is “which step needs a model at all, and how much of one”

Intelligence did get cheaper

It was never going to be too cheap to waste

Set the mode once, per place

Script what never changes

Check the receipt

Then stop picking models

That is mode engineering
