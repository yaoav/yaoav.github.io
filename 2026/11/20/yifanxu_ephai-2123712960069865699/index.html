What Should a Personal Agent Remember About Me?

发表于2026-11-20|行业观察
|浏览量:

本文转载自 X 博主 @yifanxu_ephai（Yifan Xu） 的长文，原文链接，版权归原作者所有。

I can’t tell whether Astra 6.2 has gotten smarter. What I have noticed is how many turns it takes to get it to remove the extras. I’ll ask for a small change, and it’ll build in support for a few things I might want later. Then we spend the next several messages working our way back to the change I asked for.

I’d love to skip that conversation next time. But what should the agent write in my profile? “Prefers simple designs” sounds reasonable. What bothered me, though, was spending time on a feature I had no use for. If that same feature solves a real problem on the next project, I’d be happy to hear about it.

That’s what interests me about memory in a personal agent. It can keep a perfectly accurate record of what I said and still draw the wrong conclusion about me.

What did I mean by that?

Around ten one night, someone asked a coworker to grab a late bite at a place that serves lamb.

“I’ll pass,” the coworker said. “I was up at six thirty for a checkup.”“Did the doctor say you should avoid lamb?”

The coworker was just tired.

I like this story because you can see exactly where the conversation went sideways. One person heard “checkup.” The other figured “six thirty” explained everything. An agent with calendar access could have looked up the appointment, confirmed the time, and still missed why the coworker wanted to stay home.

I think about that when people say an agent will understand me better if I give it access to more data sources. Calendar access is useful. So is the ability to search my email. But if connecting my inbox gets me a summary of every unread message, I now have another inbox to get through. Some of those emails were unread on purpose.

I’ve heard a similar complaint about handing a question to an agent. You might have spent five minutes thinking it through yourself. Now there’s a four-page answer waiting for you, and you’re even less inclined to read it. Part of what I want from a personal agent is some judgment about what deserves my attention in the first place.

How does a remark become a preference?

The first version of a memory system can be fairly simple. Keep a profile in one file and temporary notes in another. Markdown is easy to inspect. JSON is convenient when the software needs to update individual fields. The harder questions come up a few weeks later. When does something I said in passing deserve a place in my profile? If I change my mind, which record gets updated?

One approach is to keep an observation in temporary notes until a pattern emerges across several conversations. I’d be careful about what counts as a pattern. If I ask three times in one session for the same feature to be removed, that’s one design decision. I just had to ask three times. On the other hand, if I explicitly ask the agent to remember a preference, once should be enough.

Suppose I open my profile and find “prefers to keep configuration in code.” I’d want to know where that came from. Maybe what I actually said was, “This script only needs to run once. Just put the two settings at the top.” PowerContext keeps the original prompt and a saved project memory in separate records. That lets me correct the preference and still look up why we kept the settings inline for that particular script. PowerContext’s memory design https://github.com/oceanbase/powercontext

I’d also keep a searchable archive separate from the memory an agent routinely consults. Someone described keeping an Obsidian folder for each bot and saving their conversations every day. I understand the impulse. It’s hard to know in advance which conversation you’ll want to revisit. Eventually, though, the collection grew unwieldy, and they gave up on using it. I’d happily keep old conversations around to search. I’d be more selective about which ones the agent draws on when it starts a new task.

Six months of conversations

A thousand-token profile is easy to load in full. Give the same agent six months of conversation history and the engineering problem changes. Say personal memory alone accounts for 30,000 tokens. Add tool definitions, the current instructions, and recent messages, and you could be at 70,000 or 80,000 before the agent has done much work. Even with a 200,000-token context window, what do I gain from loading a six-month-old design discussion just to rename a variable?

If I asked why we kept those two settings in the script, I’d want that discussion back. The file hasn’t changed. What the agent needs to know about it has.

One detail I like about PowerContext’s Codex integration is the budget for automatic retrieval. Before the model processes a prompt, a hook requests up to 8,000 bytes of context. The agent can retrieve more if it needs to. I don’t have a strong view on the right budget, but a sentence about the earlier decision and a reference back to the discussion would serve me well here. For the rename, the agent can get on with the edit. For the design question, it knows where to look. Codex integration documentation

That’s also how I’d test memory. I’d start by asking the agent to help me write a one-off script. Later, I’d tell it the team was taking over maintenance and ask what it would change. I’d want to see whether it remembers why we made the original decision and whether it recognizes that the reason no longer applies. I’d learn more from that exercise than from asking it to recite a list of saved preferences.

When should it interrupt me?

Suppose I’ve asked an agent to track flight prices. A seat opens up while I’m in a meeting, and the fare is a little higher than I’d hoped. Should it interrupt me?

If this is the last flight that gets me home in time for a family event, I want to hear about it. If my dates are flexible, I’m happy to wait until the meeting ends. And if I’ve given the agent a spending limit and explicitly authorized it to book a flight that meets my conditions, it can go ahead. My calendar tells it I’m busy. My travel history gives it a sense of what I usually spend. Neither tells it how much this trip matters. Permission to buy a ticket has to come from me.

One way to evaluate a personal agent is to track how often I have to step in. I’d want to look at why. If I have to repeat my budget every time it searches, that gets old. If there’s only one flight left that gets me home in time and it asks whether I’ll pay a little more, I’m glad it asked. An agent can get that number down simply by making more decisions on its own. I’d also track how often I have to undo one of those decisions.

There’s a business question here, too. An agent that knows why I need to be home on Friday can find a ticket I’d gladly pay more for. It also knows exactly what to emphasize if a booking partner offers a higher commission on that fare. I’d want to be able to ask, “Why this flight?” and get a concrete answer. Which alternatives did it consider? Did the cheaper flight arrive too late? Did the commission affect which flights it showed me? Those answers would shape how much I trust it with the next booking.

For now, I’d settle for something smaller. The next time I ask for a script I’ll only run once, give me the few lines I need and let me get on with my day. A month later, when I say the team will be maintaining it, bring up the configuration file again. I’d be glad to have that conversation. This time there’s a reason to have it.
