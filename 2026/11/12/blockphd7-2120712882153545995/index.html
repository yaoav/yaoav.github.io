文章分两部分，可以按需要读：

  • 第一部分：看懂这套方案（第一到第六节）。不碰命令，讲清楚整体结构、每一层为什么这样做、机器怎么选、哪些坑最常见。只想理解思路的话，读完这一部分就够了。

文中的软件只是举例。你换成别的代理内核、别的网关或别的客户端，方法依然成立。

第一部分：看懂这套方案

一、先想清楚：你到底要解决哪几个问题

大多数人一开始的需求是一句话：“我想在 VPS 上跑个模型代理，本机直接用。”拆开后，其实是四个独立问题：

问题 本质 对应的层 浏览器访问某些网站要用 VPS 的出口 代理与出口 出口层 其他网站继续用原来的网络或代理 规则与优先级 分流层 本机工具要有一个稳定的模型 API 地址和 Key 网关与授权 接入层 出问题时能快速定位是哪一环 分层验收 运维层

把这四件事混在一起做，是最常见的失败原因。比如节点通了就以为 API 也能用，或者 API 报错就去重新登录账号，其实问题只是本机隧道断了。

所以整套方法论只有一句话：两条链路分开建，三类凭据分开管，每一层单独验收。

二、整体架构：两条并行的链路

同一台 VPS 承担两件事，但它们是两条不同的路。

图 1：两条并行链路。上半部分是浏览器出口（链路 A），下半部分是模型 API 接入（链路 B），底部是三类必须分开管理的凭据。

链路 A：浏览器出口链

浏览器
-> 本机代理客户端（规则模式）
|- 指定网站 -> VPS 节点 -> 目标网站看到 VPS 的 IP
|- 其他指定网站 -> 原有代理节点
`- 其余网站 -> 原有规则（直连或原代理）

链路 B：模型 API 接入链

本机 AI 客户端
-> 127.0.0.1:<本地端口>
-> SSH 本地转发（加密）
-> VPS 127.0.0.1:<网关端口>
-> 模型网关（校验客户端 Key）
-> 网关保存的上游授权
-> 上游模型服务

两条链路的关键区别：

  • 链路 A 用代理协议，解决“从哪里出去”。
  • 链路 B 用 SSH 隧道，解决“怎么安全地访问 VPS 上只监听本机的服务”。
  • SSH 隧道不会让浏览器换出口；代理节点也不会让本机工具访问到 VPS 的 localhost。

想清楚这一点，后面绝大多数故障都能一眼判断属于哪条链。

三、每一层为什么这样做

整套方案的每个设计都对应一个具体的风险。理解了风险，配置细节忘了也能自己推回来。

出口层：用一台独享的 VPS，拿一个固定的出口 IP。 公共代理节点往往几百人共用，你分不清谁在上面做过什么；动态的住宅代理 IP 又会频繁变化，平台看到的是一个到处跳的用户。自己的 VPS 只有你一个人用，出口 IP 固定，至少出口这一项是稳定、可控的。节点协议选 VLESS + REALITY，目的是让非客户端的探测看到一个正常的 HTTPS 网站；这能降低被一眼认出的概率，但不保证不被识别。

分流层：只把需要的网站交给 VPS，其他照旧。 浏览器里只有少数几个网站需要固定出口，其余继续走原来的网络或代理。这些网站对应的分组里只放 VPS 一个节点，不放备用，也不允许直连。原因很简单：VPS 断了，宁可请求失败让你发现，也不要悄悄换成别的出口，而你毫不知情。

接入层：模型网关放在 VPS 上，本机通过 SSH 隧道访问。 上游账号的授权保存在 VPS 上，模型请求也从 VPS 发出去，所以平台看到的调用方始终是那台 VPS 的 IP，和你浏览器登录时的出口一致。网关只监听 VPS 本机，不对公网开放，本机通过 SSH 隧道把它“借”到自己电脑的一个本地端口上。这样既不用把服务暴露到公网，本机工具用起来又和调用本地服务一样。

凭据：三类分开管。 本机工具用的客户端 Key、登录网关管理界面的管理密钥、网关访问上游的授权凭据，是三样不同的东西，放在不同的地方，泄露的后果也不同。混在一起用，是很多“401”和“Key 泄露”问题的源头。网页登录账号不会生成 Key，它只是让网关拿到上游授权。

运维层：断了能自己恢复，坏了能快速定位。 电脑重启、休眠、换网络都可能让 SSH 隧道断开，所以隧道交给系统服务托管，断了自动重连。真出问题时，按“由近到远”的顺序查：先查本机代理和隧道，再查链路，最后才怀疑账号。很多看起来像“额度用完”“账号出问题”的报错，其实只是本机隧道断了。

手机端：只做必要操作，用完就退出。 前面的出口一致性都是在电脑上做的。手机是整套环境里最难控制的一环：它会在蜂窝网络和 WiFi 之间自动切换，代理 App 在切换时可能短暂断开，后台还有大量应用在联网。一旦代理断开时 App 还在后台联网，平台看到的就是你的真实网络。

我的做法是把手机的用途压到最小：日常对话和写代码都在电脑上，手机只在非用不可的时候打开，比如通过应用商店完成订阅付款。具体分四步：

  1. 打开前先连同一出口。手机代理 App 选中和电脑相同的 VPS 节点，用固定分组，不设备用节点、不允许直连。打开目标 App 之前，先在手机浏览器里用查 IP 的网站确认出口是 VPS。
  2. 使用期间别换网络。固定在一个 WiFi 下操作，不要边走边用、让手机在 WiFi 和蜂窝之间来回切。
  3. 用完彻底退出。操作完成后，从多任务界面把 App 划掉，不要让它常驻后台。可以顺手关掉它的后台刷新；如果它申请过定位权限，也一并关掉。
  4. 不长期在手机上保持登录。以后不需要手机端时，可以直接卸载 App。卸载会连同 App 的本地数据一起清掉，需要时再装回来。

如果订阅是通过应用商店付款的，后续的升级、取消和退款都在应用商店的订阅管理里处理，规则以应用商店为准，不要指望一定能退款。

这几条只是降低风险的习惯，不是防封保证。账号是否安全，仍然取决于你是否遵守服务条款。

四、选 VPS：先看这四点，再看价格

选机器时，比价格更重要的是这几点：

  1. CPU 架构。amd64 和 arm64 的二进制、镜像不能混用。以后迁移时也要注意。
  2. 内存。1 GB 内存可以跑代理内核加一个轻量网关，但最好给每个服务设置内存上限，再配少量 swap，避免一个服务把整台机器拖死。
  3. IP 政策。提前问清楚：能不能换 IP、换 IP 收不收费、可选的 IP 段有几个。很多小厂一个地区只有一个 /24 段，“换 IP”只是在同一段里换一个地址。
  4. 控制台能力。能否 VNC 登录、能否重装时注入 SSH 公钥。重装后 SSH 暂时连不上时，这决定了你能不能自救。

  1. 先看“Claude”一列，只留“支持”的。这一列看的是机房所在地区，香港机房一律是“不支持”，便宜也没用。

顺便纠正一个误解：换一个 IP 不代表你在各平台上的历史记录被重置。IP 只是一个信号，不是身份。

五、几个最常见的误区

  1. “ping 得通就能用。” ICMP 和 TCP 是两回事。
  2. “导入成功就能用。” 以真实握手和实际出口为准。
  3. “开了 TUN 就是全局都对了。” 要单独测 TUN 路径。
  4. “登录网页就会生成 API Key。” Key 是网关配置的，登录只是授权。
  5. “Key 给别人，他就能用。” 对方还需要能访问到网关的网络通道。
  6. “列表里有这个模型就能用。” 额度和权限要实测。
  7. “换个 IP 就重新开始了。” IP 只是一个信号。
  8. “备份了就安全。” 没验证过的备份不可靠，没加密的备份要当作机密文件保管。

六、安全与合规提醒

  • 网关只监听本机，通过 SSH 访问，不要为了方便把管理端口直接暴露到公网。
  • 分享经验时，只分享方法和脱敏后的配置片段。IP、域名、UUID、公私钥、Key、授权码、回调链接都不要出现。
  • 使用任何上游模型服务前，先读它的服务条款。通过网关调用订阅账号是否被允许、能否多人共用，都以服务方的规定为准。本文讲的是技术架构，不构成规避平台规则的建议。
  • 自建代理同样要遵守你所在地和服务器所在地的法律法规。

第二部分：实现手册

这一部分按执行顺序写，每一步开头先给验收标准。自己照着做也行，交给 AI 编程助手执行也行。执行时遵守四条规则：

  1. 本步验收没通过，就停在本步排查，不进入下一步。某一层失败时如实标记“未通过”，不要因为其他层正常就宣布整体完成。
  2. 占位符换成你自己的值。下表之外出现的端口、路径、服务名都是示例。
  3. 密钥只进配置文件。Key、私钥、UUID、授权回调链接不贴进对话，不截图。
  4. 删除、重装、覆盖配置之前先备份，并确认备份能用。

占位符 含义 VPS 的公网 IP <SSH别名> 本机 ~/.ssh/config 里给这台 VPS 起的别名 <网关端口> 模型网关在 VPS 上监听的端口，只绑定 127.0.0.1 <本地端口> SSH 隧道在本机打开的端口，客户端的 Base URL 指向它 <客户端 API Key> 网关配置里给本机工具用的 Key，不是管理密钥

总流程：分层搭建，逐层验收

下面第 0 步到第 8 步按四层推进：准备层、出口层、接入层、使用层。每一步都带一条验收标准，没通过就停在这一层排查，不往下走。

图 4：从零到可用的分层流程。每张卡片底部是该步的验收标准；右下角是日常运维时由近到远的排查顺序。

第 0 步：选好 VPS

验收：已确认 CPU 架构和内存；问清了 IP 更换政策；控制台可以 VNC 登录，重装时可以注入 SSH 公钥。

怎么选、选哪家，见第一部分第四节。

第 1 步：动手之前先清点和备份

验收：备份能解包，文件数量、哈希和数据库完整性检查都通过。

如果 VPS 上已经有服务，在重装或迁移前，先做一张依赖清单。逐项写清：

  • 应用本身：代码或镜像、配置文件、环境变量。
  • 持久数据：数据库、上传文件、授权记录。
  • 外部入口：域名、隧道、反向代理、证书。
  • 系统层：systemd 服务、定时任务、目录属主和权限。

备份时有三条原则：

  1. 数据库要做一致性快照。运行中直接复制 SQLite 文件可能拿到不完整的数据。用数据库自带的备份方法，或停写后复制，然后跑一次完整性检查。
  2. 备份要验证。至少要能解包、核对文件数量和哈希。没验证过的备份，等于没有备份。
  3. 备份里有密钥。目录权限设成仅本人可读只是访问控制，不是加密。不要随手上传网盘或发给别人。

不需要恢复的旧服务，借这次机会就别再恢复了。少一个服务，就少一个故障点。

第 2 步：建立可信的管理入口

验收：TCP 22 可达，公钥登录成功，主机校验保持开启。

先把“怎么安全地登录这台机器”定下来，后面所有操作都依赖它。

  • 只用 SSH 公钥登录，在本机 ~/.ssh/config 里给它起一个别名。
  • 重装或换 IP 后，主机指纹会变。先从可信来源（如控制台）确认新指纹，再只更新这一台机器的 known_hosts 条目。不要为了省事全局关闭主机校验。
  • 能 ping 通不代表能用。ping 走 ICMP，SSH 和代理走 TCP。要分别测：

nc -vz -w 5 22
nc -vz -w 5 443

TCP 通了也只说明端口可达，协议能不能握手，要用真实客户端去测。

第 3 步：搭出口节点（链路 A 的服务端）

验收：真实客户端握手成功，出口 IP 是 VPS 的 IP，地区符合预期。

以 VLESS + REALITY 为例，关键的设计决策有四个。

  1. 端口与职责

公网 443 交给代理内核。合法客户端走代理；其他访问交给一个 TLS “目标站点”处理。

  1. 目标站点选谁

有两种做法：

  • 借用外部大站：配置简单，但你控制不了对方。
  • 用自己的域名：在 VPS 上用 Nginx 起一个真实的 HTTPS 页面，只监听本机端口（如 127.0.0.1:8443），证书自己签发并自动续期。

如果选择自有域名，要注意：目标地址必须指向本机的那个端口，而不是同一个域名的公网 443，否则会连回代理内核自己，形成循环。

还要有正确预期：用自己的域名，只是让“非客户端访问”看到一个真实网站，不代表流量会变成访问你网站的内容，也不能保证不被识别。

  1. 域名解析

节点域名用普通 A 记录直接指向 VPS。如果你的 DNS 服务商带 CDN 代理功能（例如 Cloudflare 的橙云），节点记录要关掉代理，只做 DNS 解析，因为 CDN 不会帮你转发任意 TCP 协议。

  1. 客户端兼容参数

不同客户端对 REALITY 新特性的支持不同。一个常见的坑：服务端开启了新的密钥交换方式，客户端配置里少了对应开关，结果显示“导入成功”，实际握手失败。

经验是：

  • 以实际握手成功、并拿到预期出口 IP 作为“节点可用”的唯一标准。
  • 通用分享链接在不同客户端之间转换时，可能丢失专有字段。优先保存一份验证通过的完整客户端配置。
  • 版本固定，下载后校验官方发布的哈希；升级前先看发行说明。
  1. DNS 的启动顺序

如果节点用的是域名，而本机 DNS 又设置成“必须经过这个节点才能解析”，就会出现鸡生蛋的问题。给代理客户端单独配置可直接访问的引导 DNS，专门用来解析节点域名。

第 4 步：本地分流（链路 A 的客户端）

验收：连接面板显示目标域名命中 VPS 分组；系统代理和 TUN 两种方式分别测过。

目标是：指定网站走 VPS，原来的代理继续照常用，其余网站保持原样。

  1. 不要直接改订阅生成的配置

订阅一更新，手改的内容就没了。用客户端提供的“覆写”或“合并脚本”功能，把 VPS 节点、分组和规则注入进去。这样订阅更新后，覆写会自动重新生效。

  1. 按用途建分组

例如：

分组 成员 用途 US-VPS 只有自建 VPS 节点 需要固定出口的网站 Region-X 原代理中特定地区的节点 需要特定地区访问的网站 原有分组 保持不变 其他网站

需要固定出口的分组里，不要放备用节点，也不要放直连。VPS 断了就让请求直接失败，而不是悄悄换成别的出口，你却浑然不知。

  1. 域名要覆盖完整

一个网站往往用到多个域名。登录页、API、静态资源、视频流可能分属不同的域名后缀。只写主域名，常常导致一半请求走 VPS、一半走别处。

正确的做法是打开代理客户端的连接面板，实际访问一遍，看哪些域名出现、各自命中哪条规则，再补齐。

  1. 准备一个“测试出口”的网站

把一两个查 IP 的网站也加进 VPS 分组。这样浏览器里打开它，就能确认这条规则链的出口。但要记住：没加进规则的查 IP 网站，结果可能来自其他节点，不能拿来推断别的网站走了哪里。

  1. 系统代理和 TUN 的区别
  • 系统代理：只影响遵循系统代理设置的应用，浏览器通常都会遵循。
  • TUN（虚拟网卡）：接管更多应用的流量，适合那些不认系统代理的程序。但它同时会改变路由和 DNS 行为，问题更多。

一个实用的验证方法：同一个网站，分别用“显式指定代理”和“只靠 TUN”两种方式访问。前者成功、后者失败，基本就是 TUN 的 DNS 或路由问题，不是节点问题。打开了 TUN 不等于全应用都已经验收通过。

第 5 步：部署模型网关（链路 B 的服务端）

验收：网关只监听 127.0.0.1；不带 Key 请求返回 401，带客户端 Key 返回 200。

模型网关的作用，是把你已授权的上游账号或 API，转换成客户端能用的统一接口。部署时坚持四条原则：

  1. 只监听本机。网关绑定 127.0.0.1，不对公网开放端口。管理界面和 API 都只能通过 SSH 隧道访问。
  2. 专用用户运行。用独立系统用户和 systemd 服务运行，设置内存上限和自动重启。
  3. 配置文件和授权目录仅本人可读。授权目录里保存的是上游账号凭据，等同于账号本身。
  4. 版本固定，以该版本自带的配置示例为准。网上的教程可能用的是旧版字段。

三类凭据，绝不混用

凭据 用途 放在哪里 客户端 API Key 本机工具调用模型 客户端配置、密码管理器 管理密钥 登录网关管理界面 只有管理员保存 上游授权凭据 网关访问上游服务 只在 VPS 的授权目录里

一个常见误解是“我在网页上登录了账号，网关就会给我生成 Base URL 和 Key”。实际上，Base URL 和客户端 Key 是你部署网关时就定好的；网页登录只是让网关获得访问上游的授权。

第 6 步：SSH 隧道（链路 B 的通道）

验收：本地端口在监听；隧道进程被结束后能自动恢复。

先手动测通

ssh -N
-o ExitOnForwardFailure=yes
-o ServerAliveInterval=30
-o ServerAliveCountMax=3
-L 127.0.0.1:<本地端口>:127.0.0.1:<网关端口>
<SSH别名>

几个要点：

  • ExitOnForwardFailure 能避免“端口没绑上，却以为隧道建好了”。
  • ServerAlive* 让断线能被及时发现。
  • 启动前先检查本地端口是否已被占用，不要重复开隧道。
  • 重启、网络切换或休眠可能中断隧道。ServerAlive* 负责发现连接失效，进程退出后需要另一个机制重新启动它。

127.0.0.1** 永远指当前这台机器**。别的电脑或云端服务器拿到你的 Key，也访问不到你电脑上的本地端口。它们需要自己建立到 VPS 的隧道或私网通道。

日常使用：让 macOS 自动重连

手动开隧道适合首次测试。每天使用时，建议交给 macOS 自带的 launchd 托管：登录后启动，SSH 退出后重试。这样不必长期留着一个终端窗口。

先在 ~/.ssh/config 配好专用别名，例如 model-vps，确认它指向计划使用的 VPS，并指定正确的用户名、端口和私钥。首次连接时，从服务器控制台核对主机指纹，保存可信记录；不要用关闭主机密钥校验的方式解决连接失败。

下面是可改用的示例。本地 18080 和远端 8080 都是示例端口，必须替换为自己的配置。先停止自己手动运行的同一条隧道，确认本地端口空闲；不要停止其他 SSH 连接。

python3 - <<’PY’
import plistlib
from pathlib import Path

home = Path.home()
label = “net.example.model-gateway-tunnel”
target = home / “Library/LaunchAgents” / f”{label}.plist”
if target.exists():
raise SystemExit(“Existing file found; inspect it before changing it”)
target.parent.mkdir(parents=True, exist_ok=True)
log_dir = home / “Library/Logs/model-gateway-tunnel”
log_dir.mkdir(parents=True, exist_ok=True)
log_dir.chmod(0o700)
args = [
“/usr/bin/ssh”, “-NT”,
“-o”, “BatchMode=yes”,
“-o”, “StrictHostKeyChecking=yes”,
“-o”, “ExitOnForwardFailure=yes”,
“-o”, “ServerAliveInterval=15”,
“-o”, “ServerAliveCountMax=3”,
“-o”, “ConnectTimeout=12”,
“-o”, “ConnectionAttempts=1”,
“-o”, “ControlMaster=no”,
“-o”, “ControlPath=none”,
“-L”, “127.0.0.1:18080:127.0.0.1:8080”,
“model-vps”,
]
config = {
“Label”: label,
“ProgramArguments”: args,
“RunAtLoad”: True,
“KeepAlive”: True,
“ThrottleInterval”: 10,
“ProcessType”: “Background”,
“Umask”: 0o077,
“StandardOutPath”: str(log_dir / “stdout.log”),
“StandardErrorPath”: str(log_dir / “stderr.log”),
}
with target.open(“xb”) as output:
plistlib.dump(config, output)
target.chmod(0o600)
PY

plutil -lint “$HOME/Library/LaunchAgents/net.example.model-gateway-tunnel.plist”
launchctl bootstrap “gui/$(id -u)”
“$HOME/Library/LaunchAgents/net.example.model-gateway-tunnel.plist”

这些参数各管一件事：

  • RunAtLoad 在服务加载、用户登录后启动连接；LaunchAgent 运行依赖该用户已登录。
  • KeepAlive 在 SSH 退出后重新启动它；ThrottleInterval 限制重试频率，持续连不上时查看日志。
  • ServerAliveInterval=15 与 ServerAliveCountMax=3 在正常运行时约 45 秒连续收不到响应后判定失效。睡眠中的计时和唤醒后的网络恢复可能延迟，不能承诺开盖就立即可用。
  • BatchMode 禁止后台进程等待密码输入；若私钥需要口令，应先配置可供后台 SSH 使用的 Keychain 或 ssh-agent，并实际验证。
  • StrictHostKeyChecking=yes 保持主机身份校验。服务器重装后，先从控制台核实新指纹，再处理可信记录。
  • ControlPath=none 避免复用另一条未受托管的控制连接。这里不加 -f，让 launchd 直接管理 SSH 进程。
  • -L 127.0.0.1:… 只开放本机入口，VPS 网关也继续只监听回环地址。

验收自动恢复，不能只看“已启动”

使用示例端口时，先检查：

launchctl print “gui/$(id -u)/net.example.model-gateway-tunnel”
lsof -nP -iTCP:18080 -sTCP:LISTEN
curl –noproxy ‘*’ –max-time 10 -o /dev/null -sS
-w ‘%{http_code}\n’ http://127.0.0.1:18080/v1/models

网关配置了客户端 Key 时，未带 Key 的模型列表通常返回 401。这说明本地到网关的 HTTP 路径可达，还需要用正确的客户端 Key 验证模型列表和最小推理请求。

在没有请求运行时，可以只对这条服务做一次受控中断：

launchctl kill SIGTERM “gui/$(id -u)/net.example.model-gateway-tunnel”

随后确认 SSH 进程 PID 已变化、本地端口重新监听、API 恢复可用。某次测试几秒恢复，只能证明当时的自动重启通过；真正的睡眠唤醒还应另测，不要用进程重启试验代替。要停用服务，使用 launchctl bootout “gui/$(id -u)/net.example.model-gateway-tunnel”；只结束 SSH 会被 launchd 再次启动。

自动重连以后，IP 也要分别核对

SSH 服务固定转发到之前确认的 VPS，恢复的是链路 B。浏览器的链路 A 仍依赖代理客户端、TUN 和分流规则；它们各自都要验收：

  1. 检查 SSH 别名的 HostName。如果服务参数另设了 HostName，也要一起核对；以后换 IP 时同时更新这些位置。
  2. 在浏览器打开已明确分到 VPS 的出口检测站；再在 VPS 上查询出口，比较结果。
  3. 检查连接面板里实际的 Claude、授权域名和 YouTube 请求仍命中固定 VPS 分组。单个检测站的 IP 不能替其他域名作证。
  4. 确认固定分组里没有机场备用节点或直连选项，避免失败时换了出口。
  5. 检查网关自身和上游授权条目没有额外代理覆盖；SSH 连接到某台 VPS，并不保证网关再向外请求时也从这台 VPS 直接出去。

第 7 步：上游授权与出口一致性

验收：网关管理界面显示凭据已保存；最小推理请求成功；浏览器和 VPS 的出口分别核对过。

如果你希望“浏览器登录账号”和“VPS 调用接口”两处使用同一个出口，就要分别验证：

  1. 浏览器访问目标网站时的实际出口（用该网站自己的诊断页面最准）。
  2. VPS 访问同一网站时的出口。

链路 A 负责第一项，VPS 本身负责第二项。SSH 隧道只转发网关端口，不会改变浏览器的出口。

授权过程中最容易踩的坑是 OAuth 回调地址：

  • 授权完成后，浏览器常常会跳回 localhost:<某端口>/callback。
  • 这个 localhost 指的是你的电脑，但等着接收回调的程序可能在 VPS 上。
  • 只转发了网关端口，回调就会显示“无法连接”。这不一定是授权失败，而是回调没有送到正确的机器。

处理方法：按网关文档提供的方式提交回调结果，或者临时为这个回调端口也建立转发。回调链接里含一次性授权码，不要截图分享。

授权成功后，按这个顺序验收：

  1. 管理界面显示凭据已保存。
  2. 用客户端 Key 请求模型列表。
  3. 用一个便宜的模型发一个最小请求。
  4. 再到真实客户端里使用。

模型出现在列表里，不代表你有它的额度。遇到 429 先看错误正文，可能是额度、权限或频率限制，不一定是网络或 Key 的问题。

第 8 步：接入本机客户端

验收：在真实客户端里完成一次对话。

最容易填错的是 Base URL，要看客户端用的是哪种协议：

协议 Base URL 写法 Anthropic 兼容 http://127.0.0.1:<本地端口>，根地址，不加 /v1 OpenAI 兼容 http://127.0.0.1:<本地端口>/v1

以 Claude Code 为例，在用户设置的 env 中合并以下字段，保留你原有的其他设置：

{
“env”: {
“ANTHROPIC_BASE_URL”: “http://127.0.0.1:<本地端口>”,
“ANTHROPIC_AUTH_TOKEN”: “<客户端 API Key>”,
“ANTHROPIC_MODEL”: “<已验证可用的模型 ID>”
}
}

对于支持多个供应商的桌面客户端：

  • 新建一个自定义供应商，选对协议、填根地址或 /v1 地址、填客户端 Key。
  • 保存后用它自带的“测试模型”功能验证。
  • 如果多个供应商都提供同名模型，要明确选择“供应商限定”的模型，否则请求可能走到别的供应商。
  • 不要只看输入框里显示了圆点就认为 Key 保存成功，保存后再测试一次。
