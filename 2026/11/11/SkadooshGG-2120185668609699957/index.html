The Fable 5.2 & Mythos 5.2 Playbook: 7 Workflows You Can Set Up Today.

发表于2026-11-11|行业观察
|浏览量:

本文转载自 X 博主 @SkadooshGG（Skadoosh） 的长文，原文链接，版权归原作者所有。

Copy-paste prompts for research, coding, design, data, automation, and authorized security review, with the setup and checks each workflow needs.

Comparing three AI tools quickly turns into checking pricing pages, translating credits into actual usage, and finding out whether a feature exists on your plan. Debugging a small app can turn into tracing a request through three services. Even a spreadsheet can hide a refund, a repeated export row, and two currencies in the same total.

These are useful jobs to give the new Claude models. They have a finish line you can inspect.

I organized this playbook around seven of them. Each has a prompt you can adapt, an artifact to ask for, and a way to decide whether the work is ready. Start with the workflow closest to a task already on your desk.

Before you start: choose your route

Anthropic released Fable 5.2 and Mythos 5.2 on November 9. They share an underlying model, with different safeguards and access arrangements. Fable is the general-access route; Mythos requires approval through Anthropic’s verification programs for areas such as cybersecurity and life sciences. The release announcement explains the distinction.

Use Fable for the first six workflows. The seventh explains how to prepare an authorized security review and where verified Mythos access fits. If you have approved Mythos access, it can also handle the general workflows through that environment.

For ordinary daily work, Opus 5.5 remains Anthropic’s recommended starting point. Move to Fable when the task’s complexity warrants it. The model comparison is a better guide to that decision than assuming every task needs the newest model.

In the Claude app: select Fable 5.2 if your plan offers it. Attach the relevant files and enable the tools the task requires, such as web search. A chat can analyze uploaded material; working directly on a repository also needs a coding environment or an appropriate connection.

In Claude Code: use a current version with Fable 5.2 support. The documented minimum for the model is v2.1.321. At the Claude Code prompt, use:

The explicit ID matters. In some gateway sessions, the alias fable can resolve to an earlier version. Confirm the actual model and effort after selecting them. Organization limits and provider configuration can affect what is available. See model configuration.

In your own API integration: the Claude API IDs are claude-fable-5-2 and, with approved access, claude-mythos-5-2. Partner platforms can use different identifiers. Both support text and image input, a 1M-token context window, and up to 128K output tokens, subject to your application’s limits. Fable specifications and Mythos specifications list the details.

For file work, create one project folder with inputs and an output location. Give the agent the goal, the files it may use, and the result you expect. Keep credentials and unrelated personal files outside that scope.

1. Research a decision you can actually defend

Best starting point: Fable in a chat with search, or a coding agent with approved browsing tools.

A useful comparison needs to answer your question under your conditions. A service with the lowest advertised price can become expensive once you include the required plan, retrieval charges, or a feature sold separately.

Ask for a decision brief and a source record together. Each material claim should point to a page, document, or passage that supports it. Include the date checked, because pricing and availability move quickly.

For a first exercise, compare three tools for one narrow job: extracting structured information from the same kind of PDF, transcribing the same language, or hosting a small internal application. Give the agent the expected volume and the requirements that would rule an option out.

Use this prompt:

Check three things yourself: the price of the preferred option, the requirement most likely to disqualify it, and the most surprising claim. Open the original pages rather than relying on search snippets.

The practical trick is to keep the source record when the answer changes. If a provider updates one price, the next run can revisit that assumption and the recommendation built on it.

For an API implementation, research requires a search or retrieval tool you configure. Anthropic’s web search tool supports source citations and request limits. Its search charges are separate from model tokens. Naming a model in an API request does not configure browsing for it.

Done means: the recommendation survives those source checks, its calculations are reproducible, and the unresolved facts are named.

2. Get oriented in an unfamiliar repository

The fastest route into a codebase is usually one real user action. Follow what happens when someone submits a form, opens a document, or starts a background job.

A directory tour can tell you where files live while leaving you unable to change anything. A useful map connects an entry point to the data it reads, the state it changes, and the behavior a user sees.

Start read-only. Give Fable the repository and one question you need answered before editing.

Then choose a nearby edge case. What happens when the same action runs twice? When the user loses permission halfway through? When a background result arrives after the screen closes?

This is a good place for a diagram. Label states with their meaning to the reader: “uploading,” “cancelled,” “result saved.” Keep the file references nearby so someone can challenge the map.

Save durable project guidance after the investigation. Claude Code reads project instructions from CLAUDE.md and supports AGENTS.md under its documented loading rules. Use a short instruction file for conventions and commands, with a separate task note for current findings. The memory guide explains how these files and auto memory load.

I would keep the map small enough to update after a change. A precise explanation of one path is easier to trust than a sprawling architecture document that goes stale immediately.

3. Fix a bug with a reproduction that earns your trust

Give the agent the symptom, expected behavior, and the environment where it occurs. Ask it to reproduce the failure before changing the implementation.

Consider an order request that times out. The caller retries while the original attempt is still running. If both attempts check for an existing order before either inserts one, each can conclude it should create the order.

Having an idempotency key in the request is only the beginning. The implementation needs to enforce the intended relationship between the caller, that key, the payload, and the persisted operation.

For the order case, a database uniqueness constraint on the appropriate caller-and-request identity can protect the creation record across independent connections. A changed payload under an existing key also needs an explicit policy, such as rejecting the conflict.

Keep the claim as narrow as the mechanism. Protecting one local order table does not establish exactly-once behavior for every external payment, email, or downstream service. Trace those effects separately.

Cancellation deserves the same attention. Start a job, cancel it, then allow its pending work to resolve. Check whether the late result still commits. Also check normal completion, so the fix does not disable the useful path.

For more complex event ordering, a bounded state model can help expose paths worth testing. Lauren Tan’s pstack includes Create Formal Verification Skill and Statechart. The former creates a reusable property check; the latter works with TLA+ models and readable failure paths. Review any plugin before installing it.

The part worth adopting even without a plugin: deliberately remove the relevant guard in a scratch version and make sure the check fails. A test that stays green after the protection disappears needs investigation.

4. Turn a visual reference into a working interface

Attach a screenshot you own or have permission to use. Explain the behavior that a still image cannot show: what filters do, how a form submits, what an empty state looks like, and how the page should adapt on a phone.

For a useful first build, make a small research desk. It can hold source cards, search their text, filter verified sources, and add a new source through a form. That is enough interaction to expose whether the agent built a working page.

For the visual review, compare spacing, type size, alignment, and the information hierarchy. Then use the page. Search for an absent term. Submit a long title. Tab into the dialog. Shrink the viewport.

A screenshot of the default state gives you very little information about these interactions. Keep the acceptance list beside the reference so the agent knows which behavior to exercise.

For a second iteration, change one aspect at a time: density, layout, typography, or interaction. “Make it better” leaves too many decisions bundled together to judge the outcome cleanly.

Claude Code’s checkpointing can help rewind tracked file edits. Keep source control as well: a rewind cannot undo an email, a payment, or another external side effect, and it does not capture every change made through a shell command.

5. Audit a spreadsheet before trusting its totals

This is useful even if you never write an application. Take an export that someone normally cleans by hand and ask for the rules before the final number.

A transaction export needs a definition of what belongs in the total. Are pending entries included? How are refunds represented? Is the same event repeated across exports? Are currencies separate? Does a negative charge mean a refund, or a malformed record?

Decide those rules first. Otherwise two perfectly neat reports can disagree because they answered different questions.

Here is a compact practice case: settled USD charges of 120.00, 80.00, 0.10, and 0.20; a repeated export of the same 80.00 event; a settled USD refund of 20.00; a pending USD charge of 50.00; a failed USD charge of 40.00; an invalid negative USD charge; and a separate settled EUR charge of 70.00.

Under the rules above, the USD charges are 200.30, the USD refunds are 20.00, and the USD net is 180.30. EUR stays at 70.00. The repeated export contributes nothing extra; the pending, failed, and invalid rows stay outside the settled totals.

The distinction that matters is the event identity. Two different legitimate orders can have the same amount. Matching numbers are insufficient evidence to delete a row.

Keep the calculation alongside the report. When a new export arrives, the rules should be visible enough to reuse or deliberately change. Ask for a reconciliation explaining any difference from the old report.

6. Automate a repeatable file job

Once the spreadsheet rules are settled, turn them into a small tool. The recurring work can then run as ordinary code, with the model helping to build and maintain it.

A good first automation takes a file from one input folder, validates it, creates a report, and records which source produced that output. Start with a manual command before adding a schedule.

The report needs two identities: the input version and the calculation version. If you fix a rule, the same input may legitimately produce a new report. Include both in a production tool’s output identity or manifest.

For the first small exercise, hold the rules fixed and use the input hash as the report name. Run it twice and confirm there is still one completed output. Change one valid input row and confirm the next report reflects that change.

Then interrupt it before the final rename. You should retain the earlier completed report and have no new partial report presented as complete. That failure check is worth doing before connecting the tool to anything that runs unattended.

If the project grows, delegate independent work with clear ownership. One agent can inspect parsing while another reviews output handling. Give shared interfaces and files one owner; assign bounded tasks rather than asking a crowd to improve the same directory.

Claude Code’s subagent documentation covers tool permissions, model selection, and separate task contexts. Delegation also consumes usage, so include the workers when comparing the cost of an approach.

7. Prepare a security review, with Mythos for verified work

For an authorized review of an application you own, build the review packet before launching a broad scan. Include the application version, the permitted scope, the roles users can have, the data each role should access, and a local way to exercise the relevant behavior.

Mythos 5.2 belongs here when you have verified access. Use the approved environment and permissions for that access. Anthropic’s Cyber Verification Program describes the access route. Its Defense Access tier accepts individual applicants, including eligible independent researchers and open-source maintainers, as well as organizations. Plan requirements and approval still apply.

Without Mythos access, prepare the packet and use a generally available model for permitted everyday secure-development checks, or work with an authorized reviewer. Routine code review and patching known issues do not automatically require CVP. A specialist task blocked by safeguards may need approved access.

An access-control case makes the distinction clear. A user may be signed in and still have no right to read a particular record. Check their own record, another user’s record, a missing record, and the unauthenticated case.

If your intended behavior is to return the same response for a missing record and an inaccessible record, assert that explicitly. Otherwise the response itself may reveal that someone else’s record exists.

Have a reviewer replay each confirmed finding against the relevant version. A plausible explanation is a lead to investigate. The evidence should show the boundary that actually failed and the behavior after the correction.

The 5.2-specific adjustments worth keeping

These details are easy to miss if you carry your old setup across unchanged.

When a run stops early, name the remaining artifact and its check. Authorize routine work within scope while retaining the approval boundary for irreversible actions.

Be deliberate about code ownership. Anthropic reports that presenting a codebase as the model’s own can encourage restructuring. Define whether you want a narrow patch or broader design decisions.

Review inherited delegation instructions. Check whether the task has independent slices before telling the model to start more workers.

Specify the final report. Ask for the artifact, checked version, commands run, results, remaining gaps, and next action.

Anthropic’s Fable 5.2 prompting guide explains these behaviors. Change one instruction at a time and compare the outcome on your own tasks.

Keep your API conversation history consistent. Fable 5.2 applies the preserved-thinking prefix check to all accounts. Editing the original system prompt, tools, or earlier messages while replaying the bound thinking can produce a 400 error. Keep history append-only; put new instructions in a new turn or use the supported context-management mechanisms.

Two more integration checks: Fable 5.2 uses always-on adaptive thinking, and it does not accept forced tool_choice values of any or a named tool. Review older requests that force those settings. A custom computer-use integration should also follow the current toolset migration instructions. The 5.2 migration notes describe platform-specific exceptions and the supported replacements.

Spend reasoning where it changes the result

Fable 5.2 defaults to high on the Claude API and medium in current Claude Code. Set effort explicitly when comparing runs.

Try medium for an interactive pass. Compare it with high on a difficult task using the same acceptance checks. Raise it further when the outcome justifies the additional usage. The effort guidance explains the controls and their precedence.

Fast mode changes speed and billing. It uses the same model with a speed-oriented configuration. In Claude Code, use /fast to inspect or toggle it while on the intended model. Fable 5.2 support requires v2.1.321 or later, and subscription users pay through usage credits rather than the normal subscription rate limits. See Fast mode.

At the current Claude API rates, Fable 5.2 and Mythos 5.2 cost $8 per million input tokens and $40 per million output tokens at standard speed. Fast mode costs $16 and $80 respectively. With 100,000 uncached input tokens and 10,000 billable output tokens, that is $1.20 standard or $2.40 fast, before tool charges and other applicable modifiers. Use your provider’s actual usage records when reconciling a bill. API pricing.

Cache stable context in an API workflow. Keep the reusable project brief and tool definitions at the beginning of the prompt. Cache hits require the matching prefix to stay identical. Fable’s current five-minute cache write costs $10 per million tokens; a cache read costs $0.20. Count the write, any uncached suffix, and output when comparing costs. The caching guide explains eligibility, cache lifetime, and implementation.

Use Advisor at decision points when the task calls for it. Claude Code can let a supported main model consult a stronger advisor. For example, Opus can handle the task while Fable advises on a difficult decision. Inspect the available choices with /advisor; pairings, account access and organization settings apply.

Advisor is experimental. Each consultation reads the conversation and adds advisor usage, which can grow expensive in a long session. Its own read is currently uncached. Decide whether the better guidance offsets that additional work. The Advisor guide covers configuration and billing.

Keep the next run easy to resume

Before closing a long session, save the goal, changed files, tested source version, decisions, open questions, and the next bounded action in the project. On return, ask the agent to compare that note with the actual files before continuing.

The same habit improves all seven workflows. Research resumes from its source record. A bug fix resumes from its reproduction. A data audit resumes from its rules and input hash. An automation resumes from a known completed output.

Pick one unfinished task today and run the matching workflow. Keep its prompt, inputs, output, and acceptance check together so the second run starts with something solid.
