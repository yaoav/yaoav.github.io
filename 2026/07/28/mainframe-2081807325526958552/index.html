How to get started with cloud agents (escape your local minimum)

发表于2026-07-28|行业观察
|浏览量:

本文转载自 X 博主 @mainframe（Mainframe） 的长文，原文链接，版权归原作者所有。

2026 is the year that coding moves to the cloud as people start running more agents, longer. Labs like SpaceXAI already use cloud agents for the majority of their PRs. And top startups like Ramp and Harvey have their own cloud agent systems.

The vast majority of people I talk to feel unprepared however. They’re used to running a few agents locally, and don’t know how to move to the cloud. Worse, their codebases are full of patterns that make it difficult to make the jump.

To help, we at @mainframe wrote down everything we know about getting started. I myself have exclusively used cloud agents since January, run them autonomously for long stretches of time, and have built internal cloud agent infra.

It’s time to escape your local minimum.

**Why cloud agents
**Agents need their own computer to be able to run for days/weeks/months and test their work (safely!) Your machine won’t cut it when you have hundreds of agents that run for days.

Besides, cloud agents give you lots of other benefits. Such as desktop recordings proving a PR works, which comes out of the box with most hosted solutions. And the ability to do work from wherever you are — whether that’s via Slack or a mobile app.

They also make it easier for other roles, like designers and PMs, to contribute to product since they no longer have to setup a machine.

Read the original Ramp Inspect blog post for a deeper sense of why cloud agents matter.

**Picking your cloud agent
**At this point there already are thousands of cloud agent offerings. I like to use one of these four: Conductor Cloud, Cursor, Devin, or Open-Inspect. You should probably start with any of the first three before you start self hosting. Disclosure: I have received both Cursor and Devin credits, although I would’ve recommended them regardless.

Conductor Cloud is great if you’re already used to the Conductor UX, and want to use your OpenAI/Anthropic sub. While it’s new and less feature-rich than Cursor/Devin, it has all the essentials and the quality you’re used to from a Conductor product.

Cursor is the best choice if you’re already in their ecosystem and either a) use Glass to occasionally run agents locally, b) want a native iOS app, or c) use Grok Bot.

If the above doesn’t apply to you, then Devin is the clear winner. They have the best overall UX and feature set since Devin was a cloud agent from day one. Surprisingly, its mobile website is so good that it’s also the best mobile experience of all four.

Open-Inspect is what you reach for if you want to self-host. Either because you want more governance, control over features, or (like Conductor Cloud) be able to use your subscriptions.

Setting up your cloud agent
Every cloud agent works the same. You tell the platform what dependencies your VM needs, that it can preinstall at build, and how to start your repo. In the case of Cursor and Devin, an agent will try and figure this out autonomously.

Conductor Cloud, Devin, and Cursor all let you define your install and start scripts in code, which I highly recommend. These platforms also need secrets to run your repo, that they’ll ask you to enter via their UI.

If you’re lucky, your codebase works once you finish onboarding. Try it by having a cloud agent do a task that touches both frontend and backend.

Most likely, it’ll trip up somewhere or have limited success because it can’t do everything you can. The rest of the article will cover the various ways in which you’ll want to improve your setup.

**Tip 1: Make your stack parallelizable
**If you’ve never thought about what happens when a cloud agent runs your repository, there might be unintended consequences.

For example, one cloud agent might undo the work of another agent because they’re using the same database. This is a bigger concern with cloud agents than local agents, since you’ll run many more agents simultaneously.

To prevent this failure mode, look over your entire the system (the server, the database etc.) and ask yourself “What will happen if N agents run this in parallel?” If you’re lucky, you happened to have already done this for git worktrees.

Example of failures look like this: you use Convex and forget that every developer has a single cloud instance. In which case you should use Convex agent mode instead. Or use Modal functions but forget to make sure every agent spins up a unique one.

You might need to get creative. For example, since Mainframe is a Github app, we give every agent the tools to quickly spin up their individual one — something we’d assumed was impossible. We did the same thing when we were making a Slack app.

You might also not be able to make all parts of your system local. In which case you’ll e.g. need to use tunnels to make sure your remote services can reach your local ones.

While you technically don’t have to worry about ports with cloud agents — since every agent has its own VM — I also like to make sure that port collisions can’t happen. That way you’ll be able to use this setup locally with worktrees, too.

**Tip 2: Dedicated agent secrets
**Don’t give your cloud agents the same secrets as humans. Use dedicated secrets with limited permissions. Because cloud agents run in a VM for a long time, they’ll find and exploit any permission hole so it’s important you keep them on a tight leash. You also want to be able to attribute actions to your agent vs. a human.

At Mainframe, we use the secrets manager Infisical to gather all agent secrets in a single place and control access.

**Tip 3: Give your agent access to real data
**Your cloud agent need real data to do its job. Be sure to give it access to seed script(s) that quickly populate the machine with “real” data, like test accounts in various states.

It’s worth considering a “frontend mode” that lets the agent run your app’s frontend with the staging backend. Note that whatever you do here benefits human UX too!

**Tip 4: Make your agent able to see and do everything you can
**One of the benefits of Cursor and Devin is that their cloud agents are instructed to test features exhaustively while also recording their computer’s screen. Unfortunately you won’t get any of the benefits if your agent isn’t able to test something because they’re e.g. not able to log in.

It’s important that you don’t give up before your agent is able to do everything you can.

Anything can become agent accessible. For example, you can give your agent an iOS simulator via Limrun or Revyl. Hand your agent its own email, that it can use to sign into services, using AgentMail.

Creativity is key. Our agent even has its own GitHub account so it can use its browser to simulate any scenario our GitHub app might face.
**
Tip 5: Make your agents go fast
**Don’t stop now that your agent is able to run your app completely. While it may work, it’s probably slow for your agent to run and test everything. This can become detrimental since e.g. 20 minutes of needless slowdown bogs down your entire pipeline. Some services your agent uses — like the iOS simulators — might also charge for this time.

Watch back the videos your agents record and see how you can save them time. For example, you might be able to provide a CLI command to skip past sign-in if you notice agents spend a long time on OAuth. Or create skills that let your agent quickly test features using Playwright.

Agent experience is the new developer experience.

Just two words of caution: don’t build in backdoors for agents that attackers can exploit. And don’t optimize for speed to the point that the agents’ experience is completely different than those of humans — you still want your agent to be able to discover real UX issues in your app.

**Tip 6: Split all knowledge into skills
**At this point you might have pages of instructions describing how agents can run and test various parts of your app. It’s tempting to keep all of this in a single AGENTS.md but we’ve found that adherence goes down if you do. Instead, split up the instructions into skills that the agent can load just in time. For example, you might create a mobile testing skill that tells your agent how to spin up an iOS simulator.

**Tip 7: Ask your agents for feedback
**Whenever you run your agents for a long time, ask for feedback on anything that sucked about their experience. They might tell you a part of your dev stack is broken or much slower than need be.

We’ve started experimenting with a dedicated feedback channel in Slack where agents can post DX grievances.

**Tip 8: Make mobile your friend
**The worst thing you can do after becoming cloud-pilled is continue assuming that all work needs to happen in front of your computer. Download the Cursor and Conductor Cloud mobile iOS apps, or use Devin on mobile web.

Also add Cursor and Devin to Slack and spin up your first agent.
Slack is important because it’ll also teach your designers, PMs, and other roles that development is easy now™

You’re free, no longer chained to your desk.

**Escape the local minimum
**If you did all of this, your setup is no longer local and ready for the upcoming increases in agent capabilities. Remember, you don’t have to do this all in one day.

Once you’ve spent some time with hosted solutions, you can choose to self-host cloud agents via e.g. Open-Inspect. There’s a strong argument to be made that you should own this infrastructure because it’s so fundamental to your company. It’s also much cheaper. That being said, there’s a lot of hidden work hosted solutions do under the hood and I personally love the UX they provide.

Now that you’re out of the local minimum, try pushing your cloud agent use to see where the boundaries are. The real benefits of cloud show when you start running them overnight, and in quantities you’ve never done before.

Let me know if you have any questions,
Vincent
